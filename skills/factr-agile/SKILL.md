# FACTR Agile

Version 0.1.0. Apply FACTR Core's behavioral methodology to decomposition and backlog refinement. SPLIT and SHAPE are capabilities, not stages the user must invoke.

## Apply the shared foundation

Read [the bundled Core contract](references/core/contract.md) once when applying this skill; reuse it when already available and unchanged. It owns falsifiable assertion anatomy, bounded inference, source support, observations, and formal acceptance. Its broader engineering capabilities supply reasoning principles; this product's deliverables are decomposition and backlog artifacts.

Use supplied notes, requirements, architecture descriptions, and existing backlog items as working context. Installation does not select a task or authorize external actions. FACTR Agile has its own inputs and outputs; do not initiate FACTR Test or prepare a handoff to it.

## Choose the requested outcome

- For product decomposition or subsystem allocation, read [decomposition.md](references/decomposition.md).
- For epics, features, stories, or acceptance criteria, read [shaping.md](references/shaping.md).
- For combined decomposition and refinement, use both references in the same task and deliver the requested scope.
- Read [examples.md](references/examples.md) only when a concrete illustration would help resolve a drafting choice.

Enter directly at the requested capability. A story does not need a prior epic, decomposition, approved requirement, Understanding Map, or FACT Set. Produce one item or a coherent batch as requested; do not force a complete hierarchy or one artifact per invocation. Reuse existing source context instead of introducing an orchestration preflight.

## Preserve meaning while adding understanding

Derive scope from responsibilities, actors, triggers, states, rules, and outcomes. Keep important source values, units, timing boundaries, permissions, exceptions, and interfaces in readable prose. A list of requirement IDs cannot compensate for a generic narrative.

Make each section contribute a different purpose: capability, value where grounded, scope, constraints, acceptance, or unresolved decisions. Do not inflate sparse input into invented rationale. A concise capability statement is preferable when a meaningful actor-value narrative cannot be grounded.

Use Core's falsification reasoning to make acceptance conditions challengeable without requiring a separate claim table or test procedure. Several atomic criteria may belong to one cohesive feature or story. Do not equate an atomic criterion with a compulsory backlog item.

## Work provisionally when needed

Label material inferred or proposed behavior and its basis beside the affected item or criterion. Keep competing central interpretations as separate alternatives or describe their common supported scope. Ask only when no meaningful requested result is possible without a decision; continue the independent useful work.

Do not invent human roles, subsystem ownership, business consequences, delivery estimates, or precise thresholds to fill a template. Proposed ownership stays a hypothesis. Unknown implementation choices alone do not prevent backlog refinement.

## Deliver useful, durable backlog work

Use the user's terminology and format. Default to readable Markdown and ordinary Epic, Feature, and User Story labels; use test-focused labels when requested. Answer in chat unless a saved artifact is requested or needed for the task. Create only the hierarchy, fields, and files that improve the requested output.

Preserve supplied IDs and source locators. In saved outputs retain material source bases, inference labels, assumptions, scope exclusions, and links within Agile's own decomposition and backlog work. Do not hide them solely in chat or an internal ledger. When sources change, revise affected items and identify the changed meaning without silently rewriting an accepted baseline.

Account for the selected source scope before claiming complete decomposition or coverage. Priorities, estimates, sprint commitments, and issue-tracker writes are separate requests, not default consequences of refinement. Development checks and evaluation files are maintenance tools, not runtime prerequisites.
